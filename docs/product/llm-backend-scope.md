# FIKRAH — LLM and Backend Product Scope

## Purpose

This document records confirmed product requirements for the LLM and Backend layers. It is a requirements record, not an implementation plan or API design. Do not treat open questions as settled requirements.

## Confirmed Product Scope

FIKRAH is an LLM-powered personal knowledge management application, or second brain. Users capture text notes, voice notes, and PDF documents; LLM helps turn that information into structured, interconnected knowledge.

The product experience is:

**Capture → Understand → Organize → Connect → Retrieve → Discover**

Users can manage notes, organize them into projects, improve and structure notes with LLM, discover relationships between notes, search by meaning, and ask questions about their knowledge through LLM chat.

`General` is the default project and is protected from deletion. A note is associated with the currently selected project. Users may create another project and switch to/select it to organize notes there.

Every note has a title. If the user does not provide one, LLM generates it as part of note processing after the note is saved. While generation is pending, the mobile app may show `Processing…` as a UI placeholder; this placeholder is not stored as the note title.

Deleting a project deletes all notes associated with that project. Deleting a project or note also deletes all knowledge connections and Qdrant embeddings associated with the deleted notes. Cross-store synchronization and recovery behavior still need to be specified.

After a note is saved or edited, the Backend starts durable asynchronous LLM processing. Processing continues independently of the mobile app lifecycle. If processing fails, the note is preserved and the user can request a retry. The mobile application polls the Backend to read the note and processing state. Note IDs are generated by the Backend. Mobile sends an `Idempotency-Key` for note creation and reuses it when retrying the same request after a timeout. A result from an earlier note version must not replace results for a newer saved version.

## Content Processing Boundary

- The mobile application extracts text locally from voice recordings and PDF documents.
- Original PDF files remain on the device as-is.
- The Backend and LLM services receive text only, regardless of whether it was typed directly or extracted locally from audio or a PDF.
- The LLM and Backend layers process and store the received text.
- Server-side speech-to-text, PDF text extraction, and OCR are not required.
- Mobile application development and UI implementation are outside this work's responsibility.

## Account and Data Isolation

Every user has an independent account. A user must only have access to their own:

- Notes.
- Projects.
- Embeddings.
- Knowledge connections.
- Conversations.
- Chat history.

The initial sign-in methods are email and password, and Google sign-in. Email verification and password recovery are required in the first release, using email links sent through configurable SMTP; email/password users cannot sign in before verifying their address. Verification links expire after 24 hours, password reset links after one hour, and both are single-use. Email sends have a 60-second cooldown and a maximum of five messages per email address per hour. The HTTPS base URL for links is supplied through environment configuration. For Google sign-in, the mobile application sends a Google ID token to the Backend for verification. The Backend issues a 15-minute JWT access token and a 30-day opaque refresh token, rotates refresh tokens, and supports revocation through PostgreSQL. A verified Google email matching an existing account is linked to that account automatically.

Authentication, user accounts, authorization, and enforcement of this data isolation are Backend responsibilities.

## LLM and Backend Responsibilities

The LLM layer is responsible for understanding, refining, organizing, connecting, and retrieving knowledge.

An LLM refinement proposal must remain in the same language as the original note.

For LLM chat, answers must be grounded in notes from the selected project. If those notes do not contain enough evidence to answer, the assistant must clearly say that it could not find a supported answer there.

Semantic search is scoped to the currently selected project. Chat returns a complete response in one response rather than streaming tokens. Accepting a refinement replaces the note text and starts LLM processing for the newly saved text.

The Backend layer is responsible for APIs, authentication, user accounts, data management and persistence, and communication between the mobile application and LLM services.

The LLM and Backend owner is responsible for requirements discovery, API design and mobile integration contracts, LLM capabilities and workflows, Backend functionality, data management, authentication and user isolation, and LLM/Backend integration. This role does not include mobile application development or UI implementation.

## Selected Technologies

- Backend framework: FastAPI.
- Data stores: PostgreSQL and Qdrant.
- Redis is the broker for Backend-owned asynchronous LLM processing jobs; PostgreSQL remains the source of truth for notes and processing state.
- PostgreSQL is the source of truth for accounts, projects, notes, conversations, and knowledge connections.
- Qdrant stores embeddings and the identifiers/metadata needed to retrieve matching notes.
- MongoDB is not part of the current stack; the confirmed requirements do not call for a third database.
- Deletion is authoritative in PostgreSQL and records a durable Qdrant cleanup request in the same transaction; a worker retries Qdrant cleanup until successful. Reads must validate retrieved note identifiers against PostgreSQL during the eventual-consistency window.
- PostgreSQL remains authoritative for note and processing-job state. Qdrant writes run as part of durable Celery processing jobs and are retried with the job; search validates candidate note revisions against PostgreSQL before returning them. PostgreSQL and Qdrant do not share a transaction, so temporary vector-store lag is possible. Reconciliation for a prolonged outage remains an operational concern to define before production deployment.

## Discovery Still Needed

Confirm these behaviors with the user before treating them as requirements or designing endpoints around them:

- How users edit a proposed refinement before accepting or rejecting it.
- Which languages the application must understand and use for notes, transcriptions, and search.
- Which language chat should use when the user's question and the relevant notes have different languages, or the project contains notes in multiple languages.
